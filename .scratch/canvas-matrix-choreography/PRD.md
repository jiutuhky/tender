# PRD:画布应答矩阵卡编排与卡面/详情重设计

Status: ready-for-agent

> 源自 2026-07-12 grilling 会话共识;领域词汇见 `frontend/CONTEXT.md`(中心舞台、停靠列、生成完毕、终态、解析中断、决策触发器等)。

## Problem Statement

投标经理发起新项目解析后进入工作台画布,看到的却是一张假数据的「投标文件大纲」主轴卡混在四张真实应答矩阵卡中间,并有连线指向假章节——用户误以为大纲已生成。解析进行中,四张矩阵卡散落在画布左右两翼,没有围绕「正在生成」形成视觉焦点;生成完毕后画布也没有任何布局变化,阶段感缺失。卡面预览把最致命的信息(投标截止时间、实质性条款数)埋在计数小字里;展开详情后,几百条逐条响应无法按风险快速定位,评分办法看不出分值结构,抽屉底部还挂着两个点了没反应的假按钮。

## Solution

真实模式下彻底移除 mock 主轴卡与连线。新项目进入画布时,四张应答矩阵卡以 2×2 四宫格居中呈现(中心舞台),每张卡实时反映各自槽位的解析状态,四宫格本身即进度面板。当四个槽位全部到达终态(生成完毕),四卡以平滑动画一次性飞向画布最左侧、垂直停靠(停靠列),中心区域让位给「下一步:生成投标大纲」的轻量引导占位——布局变化本身讲述「解析 → 矩阵 → 大纲」的阶段叙事。恢复/刷新已解析项目时直接呈现停靠态,不重演动画。卡面预览重排为各卡的决策触发器优先(截止倒计时、实质性风险徽标、高风险数、分值权重条);抽屉详情增加过滤、锚点、时间线、分值结构条等高效定位手段,并以真实可用的轻动作替换假按钮。

## User Stories

1. 作为投标经理,我希望新项目进入画布时不再看到假数据的大纲卡片,以免误以为投标大纲已经生成。
2. 作为投标经理,我希望解析进行中四张应答矩阵卡以 2×2 四宫格居中呈现,让我一眼聚焦「系统正在生成什么」。
3. 作为投标经理,我希望四宫格按 项目概要 → 商务应答 → 技术应答 → 评分办法 的顺序排布,与我阅读招标文件的自然顺序一致。
4. 作为投标经理,我希望解析中每张卡各自显示 等待解析 / 解析中 / 已生成 / 解析失败 的状态,把四宫格当作进度面板看。
5. 作为投标经理,我希望正在载入数据的卡面显示骨架条而非一行灰字,与「解析中」徽标形成呼应。
6. 作为投标经理,我希望四张矩阵全部出结果(含失败)时,四卡平滑飞向画布最左侧垂直排列,让我知道解析阶段结束了。
7. 作为投标经理,我希望停靠动画在数据就绪时立即触发,而不是等智能体在对话流里说完收尾语。
8. 作为投标经理,我希望停靠后中心区域出现「下一步:生成投标大纲」的轻量提示,知道流程的下一站是什么。
9. 作为投标经理,我希望停靠后左列卡片顺序与四宫格一致(概要→商务→技术→评分),空间记忆不被打乱。
10. 作为投标经理,我希望从项目列表恢复已解析的项目时,卡片直接呈现在停靠位,不必每次重看一遍飞行动画。
11. 作为投标经理,我希望刷新页面后画布同样直接呈现停靠态,与恢复路径行为一致。
12. 作为投标经理,我希望解析期间仍能自由拖拽卡片,画布不会突然「拖不动」。
13. 作为投标经理,我希望停靠触发时所有卡片(包括被我拖动过的)一起归位,归位后系统不再干预我的卡位。
14. 作为投标经理,我希望「重置画布」按当前编排阶段重铺卡位(已停靠→铺回左列,未完毕→铺回四宫格),行为可预期。
15. 作为投标经理,我希望停靠完成后(若我没动过视图)画布自动适应,停靠列与中心占位都完整可见。
16. 作为投标经理,我希望部分矩阵失败时其余卡照常停靠,失败卡以橙色「解析失败」徽标如实标注,不掩盖问题。
17. 作为投标经理,我希望点开失败卡的详情能看到错误信息和「可在对话中要求智能体重新解析」的引导,知道如何恢复。
18. 作为投标经理,我希望解析流整体异常中断时,未出结果的卡面显示「解析中断」而不是永远的「解析中」,不被假进行时欺骗。
19. 作为投标经理,我希望项目概要卡面把投标截止时间(含剩余天数倒计时)作为最醒目的一行,临近截止时变为警示色。
20. 作为投标经理,我希望项目概要卡面同时保留项目名称、预算、采购方式/评标方法,扫一眼掌握项目基本盘。
21. 作为投标经理,我希望商务/技术应答卡面把「实质性 N 项」升格为醒目的橙色★风险徽标,因为漏一条实质性条款就废标。
22. 作为投标经理,我希望技术应答卡面在存在高风险条目时显示「高风险 N」徽标,提前预警。
23. 作为投标经理,我希望商务/技术卡面保留分类条形图(top 4 分类),了解条款的类别分布。
24. 作为投标经理,我希望评分办法卡面在 价格/商务/技术 三格下显示权重占比微条,一眼判断这是价格标还是技术标。
25. 作为投标经理,我希望所有卡面计数使用等宽数字(tabular-nums),数值对齐、扫读不跳动。
26. 作为投标经理,我希望点击卡片仍以右侧抽屉展开完整详情,交互习惯不变。
27. 作为投标经理,我希望商务/技术详情顶部有 全部 / ★实质性 / 高风险 过滤签,在几百条响应里快速聚焦致命条款。
28. 作为投标经理,我希望商务/技术详情顶部有分类锚点计数签,点击即跳到对应分组。
29. 作为投标经理,我希望条目行保留 编号、标题、要求原文、来源行号,便于对照原文核验。
30. 作为投标经理,我希望项目概要详情的关键时间节点以纵向时间线呈现,投标截止节点高亮(含倒计时),已过期节点淡化。
31. 作为投标经理,我希望评分办法详情顶部有一根按占比着色的分值结构堆叠条,直观看到价格/商务/技术/其他的分值构成。
32. 作为投标经理,我希望「否决项/通过性条款」提升到评分详情最顶部的红色警示区,因为它与实质性条款同级致命。
33. 作为投标经理,我希望评分项表格按分组显示小计行,核对各组分值总和。
34. 作为投标经理,我希望矩阵详情抽屉里不再出现点了没反应的「插入到文档」「重新生成」按钮,不被假交互误导。
35. 作为投标经理,我希望抽屉里提供「复制 JSON 路径」轻动作,便于把产物位置交给同事或智能体。
36. 作为投标经理,我希望提取结果不完整(needs_review/partial)时详情内保留黄色提示条,提醒我对照原文核验。
37. 作为使用键盘的用户,我希望回车/空格打开卡片、Esc 关闭抽屉、焦点陷阱等既有无障碍行为在新设计中全部保留。
38. 作为开启了「减少动态效果」系统偏好的用户,我希望飞行编排直接切到终态布局,不播放动画。
39. 作为产品维护者,我希望 idle 演示 mockup 保持原样可用,作为设计原型的活演示面不受本次改动影响。

## Implementation Decisions

- **唯一新缝:编排阶段纯推导模块。** 输入为四个矩阵槽位状态 + 「本次浏览器会话是否亲历解析」(进入路径),输出编排阶段(中心舞台 / 停靠中 / 已停靠 / 解析中断)。画布容器只消费该模块;卡位坐标、动画触发、卡面状态均挂在这条缝下游,不另开缝。
- **生成完毕的判定**采用槽位信号:四槽位全部终态(`ready` 或 `error`)即触发停靠,`error` 计入终态;与对话相位、流是否收尾解耦。天然覆盖恢复场景与部分失败场景。
- **亲历标记不持久化**:仅存于会话内存。从解析启动走过来的会话播放飞行动画;恢复/刷新路径装载完成直接落停靠位。
- **真实模式移除 mock 主轴卡与连线**;真实模式不再渲染任何连线层。演示模式(idle mockup)完全不动。
- **中心舞台布局**:2×2 四宫格居中,顺序 概要→商务→技术→评分;停靠列沿画布最左侧同序垂直排列;卡宽维持 232 不变。
- **编排优先的拖拽策略**:全程允许拖拽;停靠触发时一次性接管全部卡位(含被拖过的),之后不再干预。「重置画布」按当前编排阶段重铺。
- **停靠完成后**,若用户未主动操作过视图(既有 touched 语义),自动适应画布。
- **中心占位**为非交互纯提示(「下一步:生成投标大纲」),为未来真实大纲生成预留舞台;大纲真实化时另立实体。
- **失败呈现**:部分失败照常停靠,失败卡橙色徽标;全盘失败(流中断且有槽位未终态)定格中心舞台,未终态卡面翻「解析中断」态。本迭代不做单矩阵定向重试(需后端指令契约),失败恢复走对话,抽屉内给引导文案。
- **卡面预览重排**(决策触发器优先):概要卡置顶截止日期+剩余天数(临近变警示色);商务/技术卡实质性数升格为★橙色徽标、技术卡追加高风险计数;评分卡三格下加权重占比微条;loading 态骨架条;计数一律 tabular-nums。
- **抽屉详情**:维持右侧抽屉形态(复用既有焦点陷阱/Esc/无障碍基建)。商务/技术加过滤签(全部/★实质性/高风险)与分类锚点;概要时间节点升级纵向时间线(截止高亮、过期淡化);评分加分值结构堆叠条、否决项置顶红区、分组小计。矩阵卡抽屉移除「插入到文档」「重新生成」假按钮,换「复制 JSON 路径」+失败态对话引导;mock 卡抽屉不动。
- **动画一律 gsap**(项目约定,不手写 CSS keyframes):停靠飞行含 stagger;`prefers-reduced-motion` 时直切终态。
- **数据流不变**:矩阵数据唯一事实来源仍是 workspace store 槽位,卡面/详情订阅 store,不经卡片实例传递;store 的 rAF 事件批处理不受本特性触碰。
- **纯前端迭代**:不改后端、不改 SSE 契约、不改矩阵 JSON schema。
- **实现前调用 `frost-design` 与 `design-taste-frontend` skill** 校准品牌规范与设计品味;样式走语义化 className 与画布作用域 CSS 变量,遵守 mono 白名单与浅色背景硬约束。

## Testing Decisions

- 前端无测试框架,质量门为 `pnpm typecheck`(strict + noUncheckedIndexedAccess)+ `pnpm lint`,二者必须全绿。
- 好的验证只观察外部行为:画布呈现的布局阶段、卡面徽标文案、动画有无,而非组件内部状态。
- 编排阶段纯推导模块是本特性唯一的单元可测点(纯函数、无 DOM 依赖);未来引入测试框架时补测的对象就是它,用例即 PRD 中的编排场景矩阵(四槽状态 × 进入路径)。
- 浏览器走查场景(chrome-devtools 驱动):新项目全程(四宫格→逐卡就绪→停靠→占位出现)、恢复路径直接停靠、部分失败停靠、全盘失败定格中断态、拖拽后停靠接管、重置画布两阶段行为、reduced-motion 直切、键盘开卡/Esc 关抽屉。
- 先例参考:仓库既有验收方式为「双轴评审 + 门控实跑」(见 M1 工作项),本特性沿用同精神——门控为 typecheck/lint,实跑为上述走查清单。

## Out of Scope

- idle 演示 mockup 的任何改动(含其卡片、dock、连线与主轴卡)。
- 单矩阵定向重试(需要后端指令契约配合)。
- 真实投标大纲的生成与呈现(中心占位仅为提示,不承载交互)。
- 后端、SSE 消息契约、矩阵 JSON schema 的任何变更。
- 恢复路径的对话 timeline 回放(维持现状:恢复只装载矩阵结果)。
- 引入前端测试框架。
