# 投标文件编制域 —— 从「读懂招标文件」到「交出投标文件」

> 产品级总纲。本文覆盖 Prose 下半场的流程、交互、架构与路线；单张实现票另立于 `issues/`。
> 调研日期 2026-08-25。现状基线：`feat/trace-preview-layer`（四矩阵抽取 + 溯源预览已成）。

---

## 0. 结论先行

**一句话定位**：Prose 不是「AI 帮你把标书写出来」，是**「AI 让你不废标、不丢分，并让标书里的每一句话都指得出依据」**。

三条判断决定了下半场的全部设计：

1. **上半场和下半场是两类问题。** 抽取有唯一正确答案（span 对不对，可自动门禁）；写作没有。所以下半场不能再造一条抽取管线，必须**把「写得好不好」降解成三个可判定的问题**：覆盖（每条要求/每个评分点是否有章节响应）、有据（每个事实断言是否指向可核验的企业资产）、合规（格式与废标项是否满足）。这三条恰好是三类链接，而不是三个 LLM 评审。

2. **大纲不是新东西，它是应答矩阵缺的那三列。** 联邦提案界的成熟做法是把 Section L（提交须知）与 Section M（评分办法）交叉挂到同一行上，让写作者答的是记分卡而不是须知。我们的 `business` ≈ Section L、`scoring` ≈ Section M，缺的正是「谁来答 / 答在哪一节 / 审到什么程度」这三列。**章节树就是那三列的载体**——它不是 AI 自由发挥的目录，是记分卡的投影，因此**覆盖闭合可以做成硬门禁**。

3. **结构入库，正文入文件。** 矩阵那套「行级工具面 + 校验 + 审计」用在自由文本上是灾难（写一段话调十次工具）。章节的**元数据/链接/状态**进对象库，**正文本体留 workspace markdown**，版本交给已有的 project git（ADR 0007）。这是下半场最重要的一条架构分界线。

**五道闸门**（闸门之间 agent 放开跑，闸门上人确权）：

| 闸门 | 名字 | 人确权什么 | 硬门禁 |
|---|---|---|---|
| G0 | 读懂 | 四矩阵条目 | 校验 all_pass + publish ✅已完成 |
| G1 | 定策 | 章节树与挂接关系 | **覆盖闭合**：每条 mandatory / 每个评分项至少挂一节 |
| G2 | 备料 | 缺料认领 | **有据可查**：强制项对应证据非空 |
| G3 | 成文 | 逐节验收 | **断言有据**：事实性断言带锚记 |
| G4 | 合规 | 逐条销项 | 确定性检查零 error |
| G5 | 成册 | 终稿签发 | 排版规则全通过 |

**下一步**：M1 做「骨架贯通」（G1 + 覆盖闭合 + 骨架主视图），同时并行做一个**排版保真度 spike**——它是全局最大的技术风险，越早证伪越好。

## 1. 我们站在哪里

上半场攒下的东西比「能解析招标文件」值钱得多：

| 资产 | 为什么是下半场的地基 |
|---|---|
| **对象库为唯一事实来源**（ADR 0008） | 校验/审计/并发裁决收口在服务层，双 adapter（MCP 给 agent、REST 给前端）。新增对象域是**扩表**，不是重造 |
| **行级溯源**（document_id + line_span） | 上半场是「条目→招标原文」；下半场是「正文→企业事实」。**同一套溯源语汇复用两次** |
| **人机共管的行级状态**（confirmed / response_status + actor 审计） | 「AI 写、人确权」的交互底座已经跑通一遍，章节验收直接沿用 |
| **Project 工作区 + Run 租约**（ADR 0007） | 章节级 fan-out 并行**在架构上已预埋**（Run 实体、路径锁、checkpoint），M3 期只差实现 |
| **真沙箱**（smolvm/Firecracker + bash + 文件工具） | 竞品是 RAG 填空，我们能跑代码：报价表核算、格式转换、图表生成、批量处理 |
| **门禁纪律**（draft → validate → publish） | 「质量不是评出来的，是门禁挡出来的」这条产品哲学已经在矩阵上验证过 |
| **画布编排语汇**（中心舞台 / 停靠列 / 抽屉 / 预览层） | 撰写期主视图可以在同一套空间语法里长出来，不需要新发明交互 |

**上半场解决的本质问题**：把「招标文件说了什么」从人的脑子里搬到了一个可校验、可审计、可协作的结构里。

**下半场要解决的**：把「我们打算怎么答」也搬进同一个结构里，并让两者之间的每一条连线都可查。

## 2. 下半场的本质约束

### 2.1 抽取与生成的可判定性鸿沟

抽取错了能自动发现（`line_span` 指向的原文对不对得上），写得差却没有自动信号。硬把 LLM 当评委（「给这段打分」）是把不可判定问题伪装成可判定，产品上会反噬——用户第一次发现「AI 说 92 分的段落评委给了 6/15」就再也不信这个数字了。

**所以：Prose 永远不预测得分**（这条纪律在已废弃的 ADR 0005 里就立过，依然正确）。我们只报三种确定性事实：

- **覆盖**：这条要求有没有章节答它 → 查链接表，SQL 就能算
- **有据**：这句承诺背后有没有一份资产 → 查锚记，确定性解析
- **合规**：格式与废标项 → 规则引擎

三者都是「有/无」，不是「好/坏」。**把不可判定的部分整个交还给人**，我们只保证他做判断时信息是全的。

### 2.2 中国标书的五条硬约束（决定产品形态）

1. **章节式长文档，不是问答式。** 欧美 RFP 是一问一答（Loopio/Responsive 的 Q&A 库模型因此成立），中国技术标是几十上百页连续论述。**Q&A 复用模型在这里不成立**，必须是大纲驱动的长文生成。
2. **评分办法是唯一写作宪法。** 内容不为读者写，为评委的打分动作写——评委要在指定章节找到得分点。这是「大纲=记分卡投影」的现实依据。
3. **废标项是生死线。** 一条不满足全盘归零，且往往是格式类的（少一份证明、漏一个签字、超页数）。**合规检查的价值高于内容生成的价值**，这是国内市场与欧美市场最大的产品差异。
4. **格式即合规。** 正本/副本份数、装订成册、目录、页码、公章与骑缝章位置、密封袋标识——这些不是「美化」，是废标条件。**因此排版必须是确定性管线，不能让 LLM 掷骰子。**
5. **终点不是「提交」，是「一份能导进投标客户端的文件」。** 电子标的 CA 签章与加密由交易平台的编制工具完成，我们**不碰签章加密**，我们的交付物是喂给它的规范 docx/pdf。这条边界要在产品里说清楚，否则用户预期会错位。

## 3. 竞争坐标

| 流派 | 代表 | 模型 | 强在哪 | 我们的空位 |
|---|---|---|---|---|
| **欧美 RFP 派** | Loopio、Responsive、Inventive | 知识库问答对 + 合规矩阵自动化 + 项目管理 | 团队协作与复用成熟；Responsive 的 compliance matrix 自动化被业界认可 | 问答模型不适配中国章节式长标；无沙箱执行能力 |
| **提案智能派** | AutogenAI | RAG + 证据分级（证言→案例→前后数据→对比分析）+ win themes + 弱点扫描 | **证据分级模型值得直接借鉴**；「不只是写作工具，是思考工具」的定位正确 | 英文语域；无格式合规；无溯源到原文的行级证据 |
| **国内编标派** | 钛投标、易中标等 | 垂类模型 + 行业模板 + 一键生成 + AI 排版导出 + 企业资源库 | 排版导出与资源库沉淀已是标配；**贴近国内格式合规** | 模板化生成同质严重；**无逐条覆盖闭合、无断言溯源**——生成快但不敢直接用，人还要通读一遍 |
| **通用 agent 派** | Claude Cowork、Trae Work、Manus | 共享工作台 + agent 产出制品 + 检查点审批 | 交互范式先进（计划审批、活动日志、可中断） | 无领域门禁，长文档一致性与格式合规无从谈起 |

**我们的空位很清楚**：国内编标派有格式与模板，欧美派有复用与合规矩阵，通用 agent 派有交互范式——**没有人把「逐条覆盖闭合 + 断言级溯源 + 真执行沙箱」三件事同时做在中国标书场景里**。

护城河按可防御性排序：

1. **双向溯源**（招标原文 ↔ 矩阵条目 ↔ 章节 ↔ 企业证据）。这是结构性资产，不是模型能力，对手补不上——他们的生成物从第一天起就没有链接。
2. **记分卡驱动的骨架 + 覆盖闭合门禁**。把「写得好」变成可判定，是唯一能让用户敢直接用的路径。
3. **机构记忆复利**。证据库随投标次数增长，越用越难迁走。
4. **真沙箱执行**。报价核算、格式转换、批量处理——RAG 产品做不到。

## 4. 五道闸门（流程设计）

设计原则：**闸门之间 agent 尽量放开跑，闸门上人只做一次高杠杆确权。** 反面是每步都问一句（用户疲劳，agent 价值归零）和全程不问（用户失控，产物不敢用）。

### G1 定策 —— 记分卡投影成骨架

- **输入**：四矩阵已发布 + 招标文件的「投标文件格式与组成」条款（`business` 矩阵 `category=bid_document` 的条目）
- **agent 做**：生成章节树（分册 → 章 → 节），逐节点挂接它要响应的 `requirement_id` 与 `scoring_id`，给出篇幅预算与证据需求提示
- **人确权**：**章节树结构 + 挂接关系**。这是全流程最高杠杆的一次人工介入——后续所有并行生成都锚定它，此处一分钟胜过后面一小时
- **硬门禁 · 覆盖闭合**：① 每条 `mandatory=true` 的要求至少挂一个节点；② 每个评分项至少挂一个节点；③ 招标文件规定的必备章节/表格一个不少。未闭合不许进 G2，未挂接项进裁决队列
- **产出对象**：`OutlineNode` + `coverage` 链接

> 设计要点：骨架**必须允许人推翻重排**。agent 生成的是初稿骨架，覆盖闭合检查在人改完之后重跑——门禁守的是闭合性，不是 agent 的方案。

### G2 备料 —— 缺料清单

- **agent 做**：逐节点推导「写这节需要什么材料」（资质证书、业绩合同、人员简历、检测报告、参数表、图纸、财报），到机构证据库匹配，产出**缺料清单**
- **人确权**：认领缺口（上传 / 指派同事 / 标记不适用并说明）
- **硬门禁 · 有据可查**：强制项与高分值项对应的证据不得为空
- **产出对象**：`EvidenceAsset`（**org 级**）+ `EvidenceRequest`（project 级缺口）

> 这是最打动用户的一环。传统流程里「缺一份三年内同类业绩合同」是开标前一晚发现的；提前到开工第二天发现，价值巨大且极易被感知。**这一环的 demo 效果可能超过章节生成本身。**

### G3 成文 —— 章节并行生成 + 逐节验收

- **agent 做**：叶子节点 fan-out，**每节点一个 Run 并行**，正文写进 `deliverables/`
- **写作简报**（`prose_get_section_brief` 的返回，是并行的接口，必须打包齐全）：
  - 本节要响应的要求原文（含 `source_refs`，可回跳招标文件）
  - 对应评分项的评分规则与分值（**写作者答的是记分卡**）
  - 可用证据资产清单（含锚记 id）
  - 篇幅预算、层级深度、必备图表
  - 全局文风与口径卡（公司名/项目名/技术路线称谓统一）
- **人确权**：逐节验收（接受 / 打回重写并附意见 / 手改）
- **硬门禁 · 断言有据**：正文中的事实性断言（金额、工期、业绩、参数、人员、承诺）必须带锚记，无锚记断言进待办
- **产出**：markdown 文件 + `SectionState`

> 并行的一致性风险是真实的。对策：① 全局口径卡随每份简报下发；② 全部成文后跑一次**交叉一致性检查**（同一事实在不同章节的表述是否冲突）——这个检查是确定性的（比对锚记指向的同一资产），不是 LLM 印象分。

### G4 合规 —— 终检

**全部由确定性检查器完成，不用 LLM 判定**：

- 覆盖闭合复检（成文后链接是否还闭合）
- 废标项逐条核（`invalid_bid_triggers` 区段已在 business 矩阵里）
- 格式规则（页数上限、字体字号、必备表格与签署位、编号唯一性、目录与正文一致）
- 报价一致性（大小写金额一致、单价×数量=合价、分项合计=总价——**这类错误是明确的废标情形，且是纯算术，最该由机器包办**）
- 偏离表生成（矩阵条目应答状态的投影视图，ADR 0008 已定形态，不设独立实体）

**人确权**：逐条销项。**门禁**：零 error。

### G5 成册 —— 装订导出

- 确定性排版管线：md → docx（pandoc + `--reference-doc` 企业模板）→ python-docx 后处理（目录域代码、页眉页脚、页码起始、封面、签章占位、正副本标识）→ 分册打包
- **人确权**：终稿签发
- **交付物**：可直接导入交易平台编制工具的规范 docx/pdf。**签章与加密不在我们边界内**（由 CA 与平台客户端完成），产品文案要写明

## 5. 交互设计

### 5.1 画布主视图的第三态

现有语汇（`frontend/CONTEXT.md`）已经给出了空间语法：**中心舞台 = 当前工作对象，停靠列 = 依据**。撰写期顺着它长即可，不发明新交互：

| 阶段 | 中心舞台 | 停靠列 |
|---|---|---|
| 解析期 | 四矩阵 2×2 四宫格 | — |
| 依据期（现状终局） | 空 | 四张矩阵卡 |
| **撰写期（新）** | **标书骨架**：分册纵列 + 章节卡按树排布 | 四张矩阵卡（降级为依据层） |

**章节卡的卡面语法**沿用现有四行语法：题名 / 主指标（本节分值或字数）/ 结构条（子节完成度）/ 信号行。新增的只有**三枚健康度徽**：覆盖 · 有据 · 合规，三态复用矩阵卡既有的「状态只在偏离常态时发声」纪律——全绿不显示，缺口才亮。

「停靠」编排（中心舞台 → 停靠列）已实现且语义完全吻合：**矩阵完成即降格为依据，让位给骨架**。这是一次编排的自然复用，不是新动画。

### 5.2 并行生成的呈现

多章节同时进行时，多张卡同时处于「进行中」态（发丝线 + 边框光束语汇已有）。关键取舍：

- **Bot 消息窗只报总控**（「12 节中 4 节进行中，2 节待验收」），不把 12 路执行流并进一条时间线——那会让消息窗变成不可读的日志瀑布
- **每节点的执行流收在该章节卡的抽屉里**。点卡 → 抽屉 → 本节 Run 的执行流 + 正文预览 + 验收动作
- 这与 Cowork/Manus 的单线程长任务不同：**我们的并行是结构化的**（大纲天然给出分区），所以能用空间（卡）而不是时间（日志）来组织

### 5.3 写作台（第三个视图层）

点章节卡的「打开正文」→ 盖满画布的写作层，**与溯源预览层同构，可直接复用其实现**（`.cv-trace-stage` 文档纸面 + 逐层退 Esc + 焦点陷阱让位）：

- **左：正文**（文档纸面，同一套排版）
- **右：写作简报**（要响应的要求原文 + 评分规则 + 可用证据 + 锚记检查）
- **就地协商**：选中正文段落 → 对 Bot 下指令（「这段换成强调运维响应时效」）。这是长文写作的刚需，也是 Cowork/Artifact 已验证的范式

### 5.4 检查点节奏

按业界 HITL 的成熟结论：**审批留给有代价、有歧义、有真实影响的决策**，其余放开。我们的五个闸门就是五个确认检查点，闸门之间只播报不打断。补两条：

- **计划审批**：G3 开跑前展示「将并行生成 12 节，预计 X 分钟」，一次批准整条轨迹，而不是逐节点问
- **随时可中断**：进行中的章节 Run 可单独停（现有 Run 实体已支持），停在哪里是可见的

## 6. 架构设计

### 6.1 对象域扩展：四域 + 三链接

在 ADR 0008 既有的结构化资产管理面上**扩表，不重造**：

```
对象域            归属      载体
─────────────────────────────────────────────
Matrix（四矩阵）   project   对象库          ✅ 已有
OutlineNode       project   对象库          🆕 G1
Section           project   对象库(元数据) + workspace md(正文)   🆕 G3
EvidenceAsset     org       对象库 + blob 存储                    🆕 G2

链接              从 → 到                        判定什么
─────────────────────────────────────────────
coverage    OutlineNode → Requirement/Scoring    覆盖
cite        Section     → EvidenceAsset          有据
trace       Requirement → Document(line_span)    溯源  ✅ 已有
```

三条链接分别支撑三个确定性门禁。**这正是被废弃的 ADR 0001 里那三类链接的直觉**——那个判断是对的，错的是当时打算另造一个「本体层」。现在用 ADR 0008 的形态（对象库 + 双 adapter + 门禁 + 审计）承接，不新起模块。

### 6.2 最重要的一条分界线：结构入库，正文入文件

| | 载体 | 理由 |
|---|---|---|
| 章节的**元数据、链接、状态** | 对象库 | 要校验、要审计、要并发裁决、前端要查询分页 |
| 章节的**正文** | `deliverables/` 下 markdown | agent 用 Read/Edit 自然操作；diff 友好；版本交给 project git（ADR 0007）；行级 CRUD 工具面对自由文本是灾难 |

ADR 0008 已明确「章节正文的 Action 收口」不做，这里把它升格为显式决策并给出正向理由。**推论**：`prose_*` 工具面**不提供写正文的工具**，只提供 `get_section_brief` / `set_section_state` / `report_section`。

### 6.3 引用怎么落地：行内锚记 + 确定性解析

正文保持自由文本，但引用必须可校验。做法：正文里写行内锚记

```markdown
我方于 2025 年完成上海张江绿色数据中心二期改造，实测 PUE 1.184[^E:P-2025-0712]。
```

一个确定性解析器扫描 markdown 提取锚记，同步成 `cite` 链接行。于是：

- 正文仍是自由文本，agent 写得自然
- 链接是确定性产物，「断言有据」门禁可以真的执行
- 导出时锚记按模板渲染（转成脚注、附件编号，或直接抹掉）
- **溯源反向可查**：点一份业绩案例，能看到它被本次投标的哪几节引用了

### 6.4 证据库与 org 落地

`EvidenceAsset` 天生是 org 级（跨项目复用是它全部价值）。这意味着 **org_id 必须从 schema 留位走到真实的登录与归属**——这是产品从「工具」变成「平台」的分水岭，也是复利护城河的起点。

借鉴 AutogenAI 的**证据分级**：证言 → 案例 → 前后数据 → 行业对比。分级进 schema，写作简报按级下发，正文的说服力层次由此可控。

### 6.5 排版导出：确定性管线（**最大技术风险**）

选型结论（search-first）：**pandoc 打底 + python-docx 后处理**，不自研排版引擎、不让 LLM 生成 docx。

| 层 | 工具 | 职责 |
|---|---|---|
| 正文转换 | pandoc + `--reference-doc=企业模板.docx` | 标题层级、段落、表格、列表映射到企业样式 |
| 结构后处理 | python-docx | 目录域代码、页眉页脚、页码起始与分节、封面页、签章占位、正副本标识 |
| 打包 | 代码 | 分册、命名规则、正副本份数 |

**风险不小**：中国标书的跨页表头重复、合并单元格、竖排表、图文混排、公章定位，markdown 表达力不够，pandoc 也不全覆盖。

> **所以 M1 期就要并行做一个排版保真度 spike**：拿一份真实历史标书，走完 md → docx 全链，逐项记录「还原不了什么」。结论会反向决定正文的中间表示——如果 markdown 撑不住，就要在 md 里引入受控的块级扩展（表格指令、图占位、分页符），而**这个决定越晚做代价越大**。

### 6.6 章节并行：落 ADR 0007 的 M3

ADR 0007 已经预埋了全部接缝：`Run` 实体（`node_generation` 类型）、路径锁（节点 Run 登记名下路径，文件工具层拒绝越界写）、Run 结束即 checkpoint、共享租约 VM。M3 期要补的是：

- 章节 fan-out 的调度（并发上限、失败重试、部分失败的呈现）
- **沙箱容量压测**：单项目 12 路并行 Run 落在一台租约 VM 上的实际表现（这是没验证过的假设）

### 6.7 工具面扩展（`prose_*` 命名沿用）

```
大纲   prose_generate_outline / prose_update_outline_node / prose_move_outline_node
       prose_link_coverage / prose_get_outline / prose_validate_outline / prose_publish_outline
章节   prose_get_section_brief / prose_set_section_state / prose_report_section
证据   prose_search_evidence / prose_get_evidence / prose_request_evidence / prose_attach_evidence
检查   prose_run_compliance_check
导出   prose_export_package
```

`prose_get_section_brief` 是并行 fan-out 的关键接口——**它决定了一个写作 subagent 在零上下文情况下能不能把这一节写对**。

### 6.8 候选 ADR 清单

下半场动工前应逐条 grilling 并落 ADR（编号从 0009 起）：

| 编号 | 决策 | 建议 |
|---|---|---|
| A | 正文载体分界线：结构入库、正文入文件 | 强烈建议先落 |
| B | 大纲是记分卡的投影；覆盖闭合是硬门禁 | 强烈建议先落 |
| C | 证据资产为 org 级一等对象；org 与登录落地 | M3 前必须落 |
| D | 正文引用用行内锚记，确定性解析成链接 | 与 A 同期 |
| E | 排版导出是确定性管线，LLM 不生成格式 | spike 后落 |
| F | 章节生成的并行单位是 Run（ADR 0007 M3 兑现） | M2 前落 |

## 7. 里程碑

每个里程碑以「能演的一段剧本」为验收，不以「模块写完了」为验收。

### M1 骨架贯通
G1 大纲域 + 覆盖闭合门禁 + 骨架主视图 + **排版 spike（并行）**

**验收剧本**：解析完成 → 一键生成骨架 → 覆盖闭合报告指出「3 条强制项无人认领」→ 人工调整章节树 → 重跑闭合 → 骨架确权。
**为什么第一**：它同时兑现了架构主张（记分卡投影）与产品主张（覆盖可判定），且**在这一步就能让用户感到「这东西懂标」**——比生成一段文字有说服力得多。

### M2 一册成文
G3 章节并行生成 + 写作台 + 逐节验收。**范围收在技术方案分册**（最长、最难、最有价值、最能体现差异）。

**验收剧本**：技术分册 12 节并行生成 → 骨架卡上逐节亮起 → 打开写作台，正文右侧就是它要响应的要求原文与评分规则 → 逐节验收 → 打回一节并附意见 → 重生成。
**证据先用 project 内上传的企业资料**，不等 org 级证据库——这样 M2 能更早出 demo 价值。

### M3 有据可依
G2 证据库（org 级）+ 缺料清单 + 锚记链接 + 登录与归属。

**验收剧本**：新建第二个项目 → 缺料清单自动命中上一个项目沉淀的业绩案例 → 一键引用 → 点该案例反查「被哪几节引用」。
**这一刻产品从工具变成平台。**

### M4 交得出去
G4 合规终检 + G5 导出装订。

**验收剧本**：终检报出「报价大小写不一致 + 缺法定代表人签字页」→ 修复销项 → 导出正本 1 副本 3 的分册 docx → 打开确认目录页码、页眉、签章位到位。

> M2 与 M3 的先后可调。当前排序的理由是「先让用户看到成文，再让他体会到复利」；若目标客户是已有大量历史标书沉淀的团队，M3 前置的说服力更强。

## 8. 风险台账

| 风险 | 等级 | 对策 |
|---|---|---|
| **排版保真度不足**，导出的 docx 还要人重排一遍——那整条链的价值就漏光了 | 🔴 最高 | M1 期 spike，结论反向决定正文中间表示 |
| 并行章节口径不一致（公司名/技术路线/承诺表述打架） | 🟠 高 | 全局口径卡随简报下发 + 成文后确定性交叉一致性检查 |
| 幻觉承诺（写出企业做不到的服务承诺、编造业绩） | 🔴 最高 | 断言有据门禁 + 承诺类语句强制锚记 + base prompt 已有的「宁可留空不可编造」升格为门禁 |
| 沙箱容量撑不住 fan-out | 🟠 高 | M2 前压测；必要时降并发或排队 |
| 骨架门禁过严导致用户绕道（「我就想随便写写」） | 🟡 中 | 门禁可显式豁免但留痕；豁免项进终检清单 |
| org/登录迟迟不落地拖住证据库 | 🟠 高 | M3 前置办；schema 已留位，成本主要在产品侧（权限模型、成员、可见性） |

## 9. 需要拍板的决策点

1. **首个里程碑的野心**：全流程薄贯通（G1→G5 各做最小可用）vs 单点做深（M1 骨架做到生产级）。本文按后者排。
2. **目标客户形态**：企业投标团队 SaaS（需 org/多租户/协作）vs 私有化部署（org 简化）vs 代写机构（多客户隔离）。**这一条直接决定 M3 的形态与优先级。**
3. **导出保真度目标**：「省 80% 排版工作」vs 「导出即可送审」。后者成本可能与整个写作域相当。
4. **M2/M3 顺序**（见上）。

---

## 10. 立即可动的三件事

1. **排版保真度 spike**（1 张票，独立可做）：真实历史标书走 md → pandoc → python-docx 全链，产出「还原不了什么」清单。它是唯一会反向改变数据模型的调研。
2. **ADR-A / ADR-B grilling**（正文载体分界线、大纲即记分卡投影）：两条都是不可轻易回退的方向性决策，按仓库惯例走 grilling 会话落 ADR。
3. **`prose_get_section_brief` 契约草案**：它是并行 fan-out 的接口，也是「写作 agent 到底需要知道什么」的具体化——**写这份契约的过程本身就会逼出大纲对象的字段设计**。
