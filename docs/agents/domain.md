# 领域文档

工程类 skill 探索代码库时应如何消费本仓库的领域文档。

## 按任务查阅

- 涉及领域术语、跨模块边界或架构设计时，查根目录的 **`CONTEXT-MAP.md`**，再按主题读相关的 `CONTEXT.md`。局部修复和文字调整可直接从相关实现开始。
- **`docs/adr/`** —— 读与你要动的领域相关的 ADR。全局/跨端决策在根 `docs/adr/`（0001 起）；上下文专属决策在 `frontend/docs/adr/`、`hagent/docs/adr/`（按需创建）。

尚未建立的上下文文档不阻塞常规工作，也不需要为此创建占位文件。若缺失信息影响本次正确性，查现有实现与决策记录，并说明仍无法确认的部分。只有任务需要记录已确定的术语或决策时才新增文档。

## 文件结构

本仓库为多上下文布局（根目录存在 `CONTEXT-MAP.md`）：

```
/
├── CONTEXT-MAP.md                ← 多上下文标记与索引
├── docs/adr/                     ← 全局/跨端决策（0001–0007 已在此）
├── frontend/
│   ├── CONTEXT.md                ← 前端上下文（暂缺，惰性创建）
│   └── docs/adr/                 ← 前端专属决策（按需创建）
└── hagent/
    ├── CONTEXT.md                ← 后端上下文（暂缺，惰性创建）
    └── docs/adr/                 ← 后端专属决策（按需创建）
```

## 用词跟词汇表

产出物命名领域概念时（issue 标题、重构提案、假设、测试名），使用对应 `CONTEXT.md` 中定义的术语，不要滑向词汇表明确避开的同义词。

若需要的概念还不在词汇表里，这本身是个信号——要么你在发明项目不用的语言（重新考虑），要么存在真实空缺（记下来交给 `/domain-modeling`）。

## 与 ADR 冲突要显式点名

若产出与既有 ADR 相抵触，明确指出而不是悄悄推翻：

> _与 ADR-0007（项目工作区与沙箱租约）相抵触——但值得重开，因为……_
