# PaddleOCR-VL-1.6 HPS 服务调用文档

修订日期：2026-09-08（UTC）。本文依据当前运行容器的接口定义、已加载模型配置和实际请求结果编写；适用于本部署，不代表其他 PaddleX/HPS 版本的接口契约。

## 1. 服务地址与准备

| 用途 | 宿主机地址 | 说明 |
|---|---|---|
| OCR HTTP 推理 | `http://127.0.0.1:8000/v2/models/layout-parsing/infer` | POST，Triton HTTP 协议 |
| 跨页重构 HTTP 推理 | `http://127.0.0.1:8000/v2/models/restructure-pages/infer` | POST，同样的 Triton 封装 |
| OCR / 跨页重构 gRPC | `127.0.0.1:8001` | 模型名分别为 `layout-parsing`、`restructure-pages` |
| Prometheus 指标 | `http://127.0.0.1:8002/metrics` | GET |
| 底层 VLM | `http://127.0.0.1:8180` | VLM 后端；完整文档 OCR 使用上面的 HPS 接口 |

远程调用时，将 `127.0.0.1` 换成服务宿主机的可达地址。在 Compose 网络 `paddleocr-vl_default` 内，HPS 地址为 `paddleocr-vl-pipeline:8000` / `paddleocr-vl-pipeline:8001`；底层 VLM 地址为 `paddleocr-vlm-server:8080`。

当前服务镜像：

- pipeline：`paddleocr-vl-1.6-hps-pipeline:h100-sm90`，镜像 ID 前缀 `1261a08116d9`。
- VLM：`paddleocr-vl-1.6-vlm-server:offline`，镜像 ID 前缀 `d0d32c04a211`。
- 客户端：`paddleocr-vl-1.6-hps-client:offline`；已验证的镜像内依赖为 `paddlex-hps-client 0.3.0`、`tritonclient 2.71.0`。

调用时先掌握以下约定：

1. Base64 文件必须同时传 `fileType`：`0` 为 PDF，`1` 为图片。
2. HTTP 请求有两层 JSON：业务请求是 Triton `BYTES` 张量里的 **JSON 字符串**。
3. HTTP 200 后还要检查内层 `errorCode == 0`，再读取 `result`。
4. `visualize: false` 时，响应会省略 `outputImages` 和 `inputImage`。
5. 字段名区分大小写。当前服务会忽略未知字段，拼错字段名可能返回成功却未应用参数。

## 2. HTTP / curl 调用

### 2.1 使用现成脚本

依赖 Bash、curl、jq 和 GNU 风格的 `base64 -w0`。不需要 Python SDK。

```bash
# PDF；输出 out_pdf/page_0.md、out_pdf/page_1.md 等
bash scripts/ocr-curl.sh testdata/sample_2page.pdf out_pdf

# 图片，并保存版面可视化图
bash scripts/ocr-curl.sh testdata/sample_table.png out_image --visualize

# 远端服务：将示例 IP 换成实际地址
HPS_HTTP=http://10.0.0.5:8000 bash scripts/ocr-curl.sh testdata/sample_2page.pdf out_remote
```

脚本按本地扩展名设置 `fileType`，`.pdf` 为 0，其余按图片传 1；默认关闭可视化，默认输出目录为 `ocr_out`。该脚本已检查 HTTP 状态及内层业务错误码，支持保存 Markdown 和返回的图片；DOCX 导出及其他参数可使用下文完整请求或 Python 示例。

### 2.2 请求与响应封装

以图片为例，HTTP 请求体如下，`<base64>` 替换为文件内容的 Base64：

```json
{
  "inputs": [
    {
      "name": "input",
      "shape": [1, 1],
      "datatype": "BYTES",
      "data": ["{\"file\":\"<base64>\",\"fileType\":1,\"visualize\":false}"]
    }
  ]
}
```

`data[0]` 必须是字符串，不能直接放业务 JSON 对象。外层响应的输出张量名为 `output`，内层业务结果位于该输出的 `data[0]`，需再次解析 JSON。当前模型只有一个输出，已有脚本使用 `.outputs[0].data[0]`。

### 2.3 完整 curl 示例

下面是可在 Bash 中直接执行的双页 PDF 示例。临时请求文件会在子 shell 结束时清理；完整响应保存到 `out_http/response.json`，首个页面的 Markdown 保存为 `out_http/page_0.md`。

```bash
(
set -euo pipefail
FILE=testdata/sample_2page.pdf
FILE_TYPE=0  # 图片改为 1，并修改 FILE
HPS_HTTP="${HPS_HTTP:-http://127.0.0.1:8000}"
mkdir -p out_http
REQ_TMP=$(mktemp -d)
trap 'rm -rf "$REQ_TMP"' EXIT

# 从文件读 Base64，避免大文件内容放入命令行参数触发 ARG_MAX
base64 -w0 "$FILE" > "$REQ_TMP/base64.txt"
jq -nc --rawfile f "$REQ_TMP/base64.txt" --argjson ft "$FILE_TYPE" \
  '{file:$f, fileType:$ft, visualize:false}' > "$REQ_TMP/payload.json"

jq -nc --rawfile payload "$REQ_TMP/payload.json" \
  '{inputs:[{name:"input",shape:[1,1],datatype:"BYTES",data:[$payload]}]}' \
  > "$REQ_TMP/request.json"

STATUS=$(curl --silent --show-error --connect-timeout 10 --max-time 300 \
  -X POST "${HPS_HTTP}/v2/models/layout-parsing/infer" \
  -H 'Content-Type: application/json' \
  --data-binary @"$REQ_TMP/request.json" \
  -o out_http/response.json -w '%{http_code}')

if [ "$STATUS" != 200 ]; then
  echo "HTTP 请求失败：$STATUS" >&2
  cat out_http/response.json >&2
  exit 1
fi

jq -er '.outputs[] | select(.name == "output") | .data[0]' \
  out_http/response.json > out_http/result.json
if ! jq -e '.errorCode == 0' out_http/result.json >/dev/null; then
  jq '{logId, errorCode, errorMsg}' out_http/result.json >&2
  exit 1
fi

jq -r '.result.layoutParsingResults[0].markdown.text' \
  out_http/result.json > out_http/page_0.md
)
```

300 秒是示例客户端超时，可以按文档大小调整。多页 Markdown 及图片的完整保存可用 §2.1 脚本或 §3.2 Python 函数。

## 3. Python / gRPC 调用

### 3.1 安装与最小示例

在已有 Python 环境中安装本地 wheel：

```bash
python3 -m pip install client/paddlex_hps_client-0.3.0-py3-none-any.whl
```

wheel 要求 `numpy>=1.24`、`tritonclient[grpc]>=2.30.0`。安装时依赖必须已安装或可从配置的包源获取。`client/requirements.txt` 只包含依赖，不会安装 `paddlex_hps_client` 本身；不要使用 `requirements.txt.official-broken`，其旧版 Triton 约束与 wheel 冲突。离线且没有可用依赖时，使用 §3.3 客户端镜像。

以下 Python 示例完整可运行：

```python
from paddlex_hps_client import triton_request, utils
from tritonclient import grpc as triton_grpc

client = triton_grpc.InferenceServerClient("127.0.0.1:8001")


def infer(model_name, payload):
    # 网络或 Triton 协议异常由 SDK 抛出；业务失败在响应内判断。
    response = triton_request(client, model_name, payload, timeout=300)
    if response.get("errorCode") != 0:
        raise RuntimeError(
            f"logId={response.get('logId')} "
            f"errorCode={response.get('errorCode')} "
            f"errorMsg={response.get('errorMsg')}"
        )
    return response


payload = {
    "file": utils.prepare_input_file("testdata/sample_2page.pdf"),
    "fileType": 0,
    "visualize": False,
}
out = infer("layout-parsing", payload)
for i, page in enumerate(out["result"]["layoutParsingResults"]):
    print(f"--- page {i} ---")
    print(page["markdown"]["text"])
```

`utils.prepare_input_file` 将本地文件转成 Base64，不会自动向请求添加 `fileType`；如果传入 URL，它会保留 URL。图片调用只需更改文件路径并设置 `fileType: 1`。

§3.2、§6、§7 的 Python 代码接在本示例后运行，复用 `client`、`infer`、`payload` 和 `out`。程序全部调用结束后执行 `client.close()`。

### 3.2 保存 Markdown、图片和 DOCX

当前部署的输出图片及 DOCX 内容为 Base64。每页使用单独目录保存，保留 Markdown 图片的相对路径。

```python
import base64
from pathlib import Path


def save_result(response, output_dir):
    if response.get("errorCode") != 0:
        raise RuntimeError(response.get("errorMsg", "业务请求失败"))
    for i, page in enumerate(response["result"]["layoutParsingResults"]):
        page_dir = Path(output_dir) / f"page_{i}"
        page_dir.mkdir(parents=True, exist_ok=True)
        markdown = page["markdown"]
        (page_dir / "doc.md").write_text(markdown["text"], encoding="utf-8")
        for relative_path, content in (markdown.get("images") or {}).items():
            image_path = (page_dir / relative_path).resolve()
            if not image_path.is_relative_to(page_dir.resolve()):
                raise ValueError(f"图片路径超出页面目录：{relative_path}")
            image_path.parent.mkdir(parents=True, exist_ok=True)
            image_path.write_bytes(base64.b64decode(content))
        for name, content in (page.get("outputImages") or {}).items():
            (page_dir / f"{Path(name).name}.jpg").write_bytes(
                base64.b64decode(content)
            )
        if page.get("inputImage"):
            (page_dir / "input.jpg").write_bytes(
                base64.b64decode(page["inputImage"])
            )
        docx = (page.get("exports") or {}).get("docx")
        if docx:
            (page_dir / "doc.docx").write_bytes(base64.b64decode(docx["content"]))


save_result(out, "out_python")
```

保存函数使用 Python 3.9+；当前客户端镜像为 Python 3.10。`visualize: false` 时仍可能返回 Markdown 所需的插图，只是省略输入图和版面可视化图。

### 3.3 离线客户端镜像

已有的 CLI 默认调用方式已验证可用：

```bash
mkdir -p out_client
docker run --rm --network paddleocr-vl_default \
  -v "$PWD/out_client":/work \
  paddleocr-vl-1.6-hps-client:offline \

```

此命令使用镜像内置样本；宿主机文件需要额外挂载后再提供容器内路径。

**当前镜像中的旧 `client.py` 存在兼容问题：不要给它加 `--no-visualization`。** 服务成功返回后，它会直接读取已省略的 `outputImages`，导致 `KeyError`。服务本身支持关闭可视化；使用 §3.1/§3.2 的代码或 curl 脚本即可。

若把 §3.1/§3.2 代码保存为 `call_ocr.py`，可以使用镜像中已有的 Python 依赖执行。先将代码里的地址改为 `paddleocr-vl-pipeline:8001`，然后：

```bash
docker run --rm --network paddleocr-vl_default \

```

## 4. layout-parsing 请求参数（全部 32 项）

下面的“默认值”是请求 schema 的默认值。`null` 表示该参数未显式指定；实际行为按对应的应用、pipeline 或 VLM 配置决定，不能统一理解为读取同一个 YAML 字段。非 nullable 字段不要显式传 `null`。配置值以本节记录的当前部署为准。

### 4.1 输入与输出控制

| 字段 | JSON 类型 | 默认值 | 说明 |
|---|---|---|---|
| `file` | string | 必填 | 文件 Base64，或服务端可访问的 URL；不接受客户端本地路径 |
| `fileType` | integer：0 / 1，或 null | null | 0=PDF，1=图片。Base64 必须显式指定；URL 仅在文件类型可由 URL 推断时允许省略 |
| `visualize` | boolean 或 null | null | 当前等效 true；传 false 后省略 `outputImages`、`inputImage` |
| `outputFormats` | array[string] 或 null | null | 额外导出格式；当前仅支持 `["docx"]`。省略或 `[]` 不额外导出；JSON/Markdown 结果仍正常返回 |
| `logId` | string 或 null | null | 自定义请求 ID；省略或空字符串时自动生成。正常通过参数校验后用于日志和响应；参数校验失败时服务会另行生成 ID |

URL 类型推断依据 URL 文件名/MIME，而非自动嗅探 Base64 内容。建议所有调用均显式传 `fileType`。URL 必须能从服务容器访问，宿主机能访问不代表容器能访问。

### 4.2 版面检测与识别

| 字段 | JSON 类型 | 默认值 | 约束与当前行为 |
|---|---|---|---|
| `useLayoutDetection` | boolean 或 null | null | 当前开启版面检测 |
| `useChartRecognition` | boolean 或 null | null | 当前关闭图表识别 |
| `useSealRecognition` | boolean 或 null | null | 当前关闭印章识别 |
| `useOcrForImageBlock` | boolean 或 null | null | 当前默认 false；控制图片块 OCR |
| `layoutThreshold` | number / object 或 null | null | 数值及字典值均须在 [0,1]；当前全局阈值 0.3 |
| `layoutNms` | boolean 或 null | null | 当前为 true |
| `layoutUnclipRatio` | number / object 或 null；数组见下文限制 | null | 正数外扩比例；当前 pipeline 配置为 `[1.0,1.0]` |
| `layoutMergeBboxesMode` | string / object 或 null | null | 字符串或字典值只能为 `large`、`small`、`union`；当前配置按类别设置 |
| `layoutShapeMode` | string | `"auto"` | 仅 `rect`、`quad`、`poly`、`auto`，控制版面形状模式 |

`layoutUnclipRatio` 的当前版本限制：schema 虽声明二元素数组，但请求传顶层 `[1.0,1.0]` 会被校验器转换成 tuple 后拒绝，返回业务 422。已实测标量 `1.0` 和字典 `{"22":[1.0,1.0]}` 可被接口接受；无需覆盖时直接省略。pipeline YAML 中已有的数组不经过这一请求校验路径，不受该缺陷影响。

### 4.3 文档预处理

| 字段 | JSON 类型 | 默认值 | 当前行为 |
|---|---|---|---|
| `useDocOrientationClassify` | boolean 或 null | null | 文档方向分类；当前未初始化预处理模块 |
| `useDocUnwarping` | boolean 或 null | null | 文档矫正；当前未初始化预处理模块 |

当前 `config/pipeline_config.yaml` 中 `use_doc_preprocessor: False`。省略这两个字段或都传 false 可正常调用；启用预处理功能会失败。已实测方向分类传 true 时返回 **HTTP 200、业务 errorCode=500**。

需要该功能时，由部署维护者先启用 `use_doc_preprocessor` 并重启 pipeline，再验证。PP-LCNet_x1_0_doc_ori 和 UVDoc 模型目录已在当前镜像中；本文未验证修改配置、重启后的预处理效果。

## 5. 响应结构与结果保存

### 5.1 成功响应

以下是解析 Triton 外层后得到的**内层业务 JSON**。内容是结构示例，`prunedResult` 仅展示部分字段；数组元素数值不是固定协议值。该例对应 `visualize: false`，没有额外导出。

```json
{
  "logId": "example-request-id",
  "errorCode": 0,
  "errorMsg": "Success",
  "result": {
    "layoutParsingResults": [
      {
        "prunedResult": {
          "width": 1068,
          "height": 331,
          "parsing_res_list": [
            {
              "block_label": "table",
              "block_content": "<table>...</table>",
              "block_bbox": [0, 9, 1060, 321],
              "block_id": 0,
              "block_order": null,
              "group_id": 0
            }
          ]
        },
        "markdown": {
          "text": "<table>...</table>",
          "images": {}
        }
      }
    ],
    "dataInfo": {"width": 1068, "height": 331, "type": "image"}
  }
}
```

| 字段 | 说明 |
|---|---|
| `logId` | 请求日志 ID，用于排查 |
| `errorCode` | 0 表示业务成功 |
| `errorMsg` | 当前成功值为 `Success`；应根据 errorCode 判断成功 |
| `result.layoutParsingResults` | 页面结果列表；普通多页 PDF 按页返回 |
| 每页 `prunedResult` | 结构化识别结果；还可含 `model_settings`、`layout_det_res`、多边形坐标等，随模式变化 |
| 每页 `markdown.text` | Markdown 文本，表格内容可能包含 HTML |
| 每页 `markdown.images` | 可选的图片相对路径 → Base64 映射，可能为空或省略 |
| 每页 `outputImages` | 可视化图片名 → Base64 映射；visualize=false 时省略 |
| 每页 `inputImage` | 输入页面图 Base64；visualize=false 时省略 |
| 每页 `exports.docx` | 请求 DOCX 导出且成功生成时返回，含 content、fileName |
| `result.dataInfo` | layout-parsing 的输入信息；独立 restructure-pages 响应不含此字段 |

PDF 的 `dataInfo` 形如：

```json
{
  "numPages": 2,
  "pages": [{"width": 2136, "height": 662}, {"width": 2318, "height": 438}],
  "type": "pdf"
}
```

当前服务代码还支持将多帧 TIFF 按图片类型读取并产生 TIFF 类型的 `dataInfo`；本次验证覆盖 PNG 和双页 PDF，没有实测 TIFF。不要把所有输入都当成单张图片。

可选模型字段值为 None 时会从响应中省略；`prunedResult` 内部自由字典仍可能包含 null。读取可选映射时使用 `(page.get("outputImages") or {})` 等写法，避免直接索引。

### 5.2 错误处理

业务失败示例：

```json
{
  "logId": "example-request-id",
  "errorCode": 422,
  "errorMsg": "File type cannot be determined"
}
```

失败时没有可供正常读取的 `result`。调用方需依次处理网络异常、HTTP/gRPC 协议错误、业务错误。

| 场景 | 本部署已观察到的结果 | 处理方式 |
|---|---|---|
| Base64 未提供 fileType | HTTP 200；业务 422，`File type cannot be determined` | 显式传 0 或 1 |
| 无效文件内容 | HTTP 200；业务 422，`Input file is invalid` | 检查文件、Base64 和类型 |
| 参数校验失败 | HTTP 200；业务 422，包含校验信息 | 按字段约束修正；不要原样重试 |
| 顶层 layoutUnclipRatio 二元素数组 | HTTP 200；业务 422，包含 `got: tuple` | 省略或使用已验证的标量形式 |
| 未初始化时启用预处理 | HTTP 200；业务 500，`Internal server error` | 用 logId 查服务日志，调整部署后验证 |
| 客户端网络超时/协议失败 | curl 或 SDK 异常，可能没有业务 JSON | 检查连接、就绪状态及负载；不要直接读取 result |

客户端超时不代表服务端已停止处理。重试前考虑任务重复执行和服务负载；本文没有假定推理请求具有去重机制。

## 6. 跨页重构

### 6.1 随 OCR 请求进行重构

接在 §3.1 后执行：

```python
out_restructured = infer("layout-parsing", {
    **payload,
    "restructurePages": True,
    "mergeTables": True,
    "relevelTitles": True,
})
```

默认不进行重构。启用后，pipeline 在进程内调用重构逻辑，并固定使用 `concatenate_pages=False`；已验证双页输入仍返回两页结果。具体表格是否合并、标题如何重排取决于文档内容。

### 6.2 对已有页面结果单独重构

HTTP 路径为 `/v2/models/restructure-pages/infer`；gRPC 模型名为 `restructure-pages`。HTTP 的两层 JSON 封装与 OCR 相同。

接在 §3.1 后，使用其原始 `out`：

```python
out_merged = infer("restructure-pages", {
    "pages": [
        {
            "prunedResult": page["prunedResult"],
            "markdownImages": page["markdown"].get("images") or {},
        }
        for page in out["result"]["layoutParsingResults"]
    ],
    "mergeTables": True,
    "relevelTitles": True,
    "concatenatePages": True,
})
print(out_merged["result"]["layoutParsingResults"][0]["markdown"]["text"])
```

需要保存时可调用 §3.2 的 `save_result(out_merged, "out_merged")`。不要直接把原始页对象作为 `pages` 使用：`markdown.images` 必须显式映射为 `markdownImages`，否则图片不会自动传给重构接口。

独立重构请求的全部 8 个字段：

| 字段 | JSON 类型 | 默认值 | 说明 |
|---|---|---|---|
| `pages` | array[object] | 必填 | 按页顺序提供上一阶段结果；每项必填 prunedResult，可选 markdownImages |
| `mergeTables` | boolean | true | 合并跨页表格 |
| `relevelTitles` | boolean | true | 重排标题层级 |
| `concatenatePages` | boolean | false | true 时拼接成一个结果；已验证双页输入返回一个结果 |
| `prettifyMarkdown` | boolean | true | 美化 Markdown |
| `showFormulaNumber` | boolean | false | 保留公式编号 |
| `outputFormats` | array[string] 或 null | null | 当前额外格式仅支持 docx |
| `logId` | string 或 null | null | 自定义请求 ID |

页对象的 `prunedResult` 是 object，`markdownImages` 是 object 或 null。应提供完整的原始 `prunedResult`，不要使用 §5 的精简展示结构作为真实重构输入。

独立模型的 Triton 实例配置为 CPU、count=1。内置重构不会增加独立模型的请求计数，因此不能用独立 `restructure-pages` 指标是否增长来判断内置重构是否执行。

## 7. 导出 Word（DOCX）

当前 `outputFormats` 仅支持 `docx`，值区分大小写。`["json"]`、`["markdown"]` 都会返回业务 422；JSON/Markdown 已包含在常规响应中。

接在 §3.1 和 §3.2 后执行：

```python
out_docx = infer("layout-parsing", {
    **payload,
    "outputFormats": ["docx"],
})
save_result(out_docx, "out_docx")
```

每页将生成 `out_docx/page_N/doc.docx`，同时保存该页 Markdown。服务返回结构为：

```json
{
  "exports": {
    "docx": {
      "content": "<base64>",
      "fileName": "generated-name.docx"
    }
  }
}
```

该结构位于每个 `layoutParsingResults` 元素中。`fileName` 是服务生成的名称，示例保存函数使用固定的页内文件名。

若要一个合并结果的 DOCX，在 §6.2 请求中同时指定 `concatenatePages: True` 和 `outputFormats: ["docx"]`，然后用同一保存函数保存。已实测双页输入合并后返回一个结果并成功保存 DOCX，文件 ZIP 结构及 `word/document.xml` 检查通过；具体排版效果仍需按实际文档检查。

## 8. 并发与超时

当前 `layout-parsing` 的 Triton 配置：dynamic batching 已开启，`max_batch_size=8`、preferred batch size 为 8、GPU 实例数为 1。单个请求仍按本文 `[1,1]` 封装；由服务调度并发请求。

以下是独立可运行的并发示例，先以两个线程验证自己的数据和资源占用：

```python
from concurrent.futures import ThreadPoolExecutor
from paddlex_hps_client import triton_request, utils
from tritonclient import grpc as triton_grpc

paths = ["testdata/sample_table.png", "testdata/sample_text.png"]
client = triton_grpc.InferenceServerClient("127.0.0.1:8001")


def run(path):
    response = triton_request(client, "layout-parsing", {
        "file": utils.prepare_input_file(path),
        "fileType": 1,
        "visualize": False,
    }, timeout=300)
    if response.get("errorCode") != 0:
        raise RuntimeError(f"{path}: {response}")
    return response


try:
    with ThreadPoolExecutor(max_workers=2) as executor:
        results = list(executor.map(run, paths))
    print(f"成功完成 {len(results)} 个请求")
finally:
    client.close()
```

这里使用的 gRPC 同步推理支持多线程共享客户端。不要把这一结论推广到 `start_stream`、`stop_stream`、`async_stream_infer` 等流式方法。

当前 pipeline 的 `Serving.extra.max_num_input_imgs: null`，没有通过该配置限制输入页数，但内存、显存和后端上下文长度仍有限。大文件及高并发应按实际机器测试；本次没有进行吞吐压测，也没有验证 gRPC 一定比 HTTP 更快。

部署维护者可结合指标检查 VLM 并发配置、版面检测 batch size 及 Triton 实例数；修改这些配置通常需要重启或重新部署。当前配置见 `config/pipeline_config.yaml`、`config/vlm_backend_config.yaml`。
